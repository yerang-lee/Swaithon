> 최신 반영: 사용자 제공 GET /products 상세 명세로 시장 상품별 탭의 실제 API 연결을 완료했습니다. 아래의 상품 목록 미연결/미확정 제안은 이전 기록이며 마지막 업데이트 절이 우선합니다.

# 시장별 가게·상품 화면

상품별 탭은 명세가 없어 명확히 표시된 예시 상품만 보여줍니다. 관심 버튼은 기존 메모리 관심 목록을 사용하며 서버 찜 연동이 아닙니다. 카테고리는 전체/채소/과일/정육/수산물/반찬/가공식품/곡물·견과/떡·베이커리/기타로 구성한 UI 제안이며 서버 분류로 확정하지 않습니다.

## 백엔드 요청안 (미확정)

시장 안의 전체 상품을 페이지·이름·카테고리로 조회할 수 있는 기능이 필요합니다. 기존 GET /products에 market_id, category, keyword, page, size 필터를 지원하면 새 경로는 없어도 됩니다. 별도로 GET /markets/{market_id}/products를 추가하는 방법도 있습니다. 둘 중 실제 지원할 방식을 정해 상세 명세와 CSV에 반영해주세요.

응답에는 상품/판매 게시물의 식별자, 상품명, 가게 ID/이름, 카테고리, 기본 가격, 할인 가격, 이미지 URL, 품절 여부, 전체 개수와 페이지 정보가 필요합니다. 상품 상세 경로의 listing_id와 음성 응답 product_id 중 상세 이동/찜/예약에 각각 어떤 ID를 사용하는지 명시해주세요. 카테고리 허용값, 할인·품절 노출 정책, 정렬 기준도 필요합니다. 거리를 표시하려면 사용자 좌표 입력 및 거리 응답도 정해야 합니다.

GET /stores/{store_id}/products를 모든 가게에 반복 호출해 합치는 방식은 시장 전체 검색/정렬/페이지 누락 문제와 요청 수 증가 때문에 현재 적용하지 않습니다.

## 카테고리 공통 규칙 요청 (미확정 제안)

카테고리는 프론트의 버튼 이름만으로 결정하지 않고 백엔드에 상품별로 저장해야 합니다. 프론트와 백엔드, 음성 AI가 동일한 코드와 표시명을 사용하도록 아래 기준을 합의해주세요. 기존 데이터와 AI 분류 체계가 있다면 그 기준을 먼저 공유해주세요.

| 코드 제안 | 표시명 | 분류 예시 |
| --- | --- | --- |
| VEGETABLE | 채소 | 당근, 감자, 버섯 |
| FRUIT | 과일 | 사과, 배 |
| MEAT_EGGS | 정육·계란 | 소고기, 돼지고기, 닭고기, 계란 |
| SEAFOOD | 수산물 | 생선, 조개, 김·미역, 건어물 |
| SIDE_DISH | 반찬 | 김치, 장아찌, 조리된 반찬 |
| PROCESSED_FOOD | 가공식품 | 두부, 유제품, 장류, 음료, 포장 가공식품 |
| GRAINS_NUTS | 곡물·견과 | 쌀, 잡곡, 콩, 견과류 |
| RICE_CAKE_BAKERY | 떡·베이커리 | 떡, 빵 |
| OTHER | 기타 | 위 분류에 해당하지 않는 상품 |

위 코드는 제안이며 현재 API가 지원하는 값으로 간주하지 않습니다. 현재 화면의 정육 명칭도 최종 합의에 맞춰 정육·계란 등으로 통일해야 합니다. 전체는 상품에 저장하는 분류가 아니라 필터 미적용 상태이며 요청 시 category를 생략합니다.

### 등록·분석·수정

- 상품 하나에 대표 카테고리 하나를 저장하는 방식으로 시작해주세요. 여러 분류에 걸치는 경우 원재료보다 판매 형태를 우선합니다. 예: 생배추는 채소, 배추김치는 반찬, 생쌀은 곡물·견과, 쌀떡은 떡·베이커리.
- 음성 AI는 같은 허용 코드 중 하나를 반환하고 서버가 검증해주세요. 현재 음성 명세의 category는 과일 같은 한글 문자열이므로, 코드를 쓸지 한글을 쓸지 최종 응답 형식을 명시해주세요. 표시명이 필요하면 category_name 등의 필드를 별도로 합의해주세요.
- 분류가 불확실하면 임의의 새 카테고리를 만들지 말고 확인 필요 상태를 반환해주세요. 사용자가 분석 결과 화면에서 분류를 확인·수정한 뒤 최종 저장할 수 있도록 앞서 요청한 분석/최종 반영 API에 카테고리 선택을 포함해주세요. 기타와 미분류 상태를 구분할지도 합의가 필요합니다.
- 가격·할인만 수정할 때 기존 카테고리를 유지하고, 명시적으로 분류를 변경할 때만 갱신해주세요. 기존 상품의 미분류 데이터 보정 정책도 정해주세요.
- 가게 업종(category)과 상품 카테고리는 별개입니다. 과일가게에서 음료를 팔 수 있으므로 가게 업종으로 모든 상품 분류를 덮어쓰면 안 됩니다.

### 조회·필터

- 시장 상품 조회에서 market_id + category + keyword 조건을 함께 적용하고, 필터링한 결과를 기준으로 total_count와 페이지를 반환해주세요. 프론트가 현재 페이지의 상품만 골라내면 다른 페이지의 상품이 누락되므로 서버에서 필터링해야 합니다.
- 지원하지 않는 카테고리 값은 400 등 합의한 오류로 반환하고, 결과가 없으면 빈 목록과 total_count=0을 반환해주세요.
- 고정 분류면 공통 enum 문서만 있어도 됩니다. 분류 추가·정렬·비활성화를 서버에서 관리하려면 카테고리 목록 조회 기능을 제공해주세요. 경로는 아직 제안하지 않으며, 코드·표시명·노출 순서·활성 여부를 포함하는 상세 명세를 공유해주세요.
- 상품 응답과 분석 응답, 최종 저장 요청, 카테고리 필터가 동일한 코드 체계를 사용하도록 맞춰주세요. 카테고리별 개수 표시가 필요해지면 별도 집계 필드도 합의해야 합니다.

카테고리 때문에 반드시 별도 API가 필요한 것은 아닙니다. 공통 분류 값, 상품 저장/분석 필드와 시장별 조회 필터 지원이 핵심입니다. 확정된 엔드포인트와 HTTP 메서드는 api-spec.csv에, 세부 필드와 분류 규칙은 상세 명세에 반영해주세요.

## 가게 상세 API 적용 (사용자 제공 상세 명세)

GET /stores/{store_id}의 store_id/store_name/market_id/market_name/category/address/description/phone/image_url을 검증하고 이름과 주소를 표시합니다. GET /stores/{store_id}/products?page=1&size=10에서 products/total_count/page/size를 사용하며 더 보기로 다음 페이지를 조회합니다. 품절 필터를 생략해 품절 상품도 표시합니다.

상품의 listing_id는 String이며 관심 목록에서도 판매 게시물 ID로 구분합니다. product_id는 표준 상품 종류 ID이므로 상세 이동 ID로 사용하지 않습니다. 상품 상세 화면은 문자열 listing_id로 연결했습니다. 상세 응답·예약·찜의 최신 필드 명세 확인은 필요합니다. 문자열 product_id를 기존 정수 예약 API에 보내지 않습니다. 테스트 상품은 기존 미리보기 상세로 연결합니다.

is_sold_out=true인 상품은 회색 배경/글자와 품절 배지를 표시하며 상세 선택을 막습니다. is_on_sale=true이고 sale_price가 유효하며 기본 가격보다 낮으면 원가를 작은 취소선으로 표시하고 할인 가격을 강조합니다. 상품명 굵기는 500이며 상품 행에 가게명/거리를 반복하지 않습니다.

아직 판매 종료/예약 마감 필드가 없어 실제 상품의 판매 종료 상태는 임의로 추정하지 않습니다. 테스트 모드에서만 판매 종료 예시를 제공합니다. 서버 상태 필드 추가가 필요합니다.

가게 상세 응답에 위도/경도가 없습니다. 카카오 주소 검색이 단일 결과를 반환하면 해당 주소 좌표에 초록 핀을 표시합니다. 범위 원/슬라이더는 없습니다. 이는 주소 기준 위치이며 개별 점포의 정확한 좌표를 보장하지 않습니다. 시장 내부 같은 부정확한 주소는 검색 실패 시 위치 안내를 표시합니다. 정확한 가게 위도/경도를 상세 응답에 추가해주세요.

사용자 실제 GPS 위치를 요청한 뒤 주소 좌표까지의 직선거리(km)를 계산하며 탐색 반경 기준 위치를 거리로 사용하지 않습니다. 위치 권한 거절 시 주소/상품 목록을 유지하고 거리 다시 시도를 제공합니다. 카카오 지도 키·도메인 설정 및 인터넷 연결이 필요합니다. 좌표가 없는 실서비스에서 키도 없으면 지도/거리는 표시할 수 없으며 이를 안내합니다.

## 시장 상품별 탭 실제 API 연결 업데이트

GET /products에 market_id/page/size/keyword/category_id/is_sold_out/is_on_sale을 전달합니다. 필터와 검색어를 바꾸면 첫 페이지로 돌아가며 이전 비동기 응답을 무시합니다. 서버가 필터링한 전체 개수(total_count) 기준으로 더 보기를 제공합니다. 프론트가 다른 가게 API를 합치거나 현재 페이지에서 상품명/카테고리를 필터링하지 않습니다. 최신순은 서버 응답 순서를 유지합니다.

상품별 탭은 예시 데이터 대신 실제 판매 게시물 목록을 사용하고 이름/가게/사진/할인가/품절과 메모리 관심 상태를 표시합니다. image_url=null은 빈 사진 영역을 표시합니다. 판매 중만은 is_sold_out=false, 할인만은 is_on_sale=true이며 기본은 두 필터를 생략합니다.

사용자 후속 지시에 따라 카테고리 코드는 9개 공통 기준을 사용하며 상품 응답은 category(코드)/category_name(표시명)를 구분합니다. 초기 제공 JSON의 category=과일처럼 표시명만 오는 응답도 표시할 수 있습니다. 숫자 category_id 전체 매핑은 미제공이므로 순서로 추측하지 않습니다. 명세 예시의 과일=2 및 조회 응답에서 확인된 ID/표시명만 카테고리 탭에 노출합니다. 따라서 첫 페이지에 나타나지 않은 분류는 아직 노출되지 않을 수 있습니다. 전체 분류를 처음부터 고정 노출하려면 category_id/code/name 전체 매핑 또는 카테고리 목록 API가 필요합니다.

목록의 listing_id/product_id/store_id/market_id/category_id는 최신 명세대로 양의 Integer를 검증합니다. 화면 라우트와 관심 상태는 listing_id를 String으로 보관하고 URL로 전달합니다. 상품 상세는 기존 문자열 ID 응답과 새 정수 ID 응답 둘 다 경로 ID와 비교할 수 있도록 보정했으며 상세 응답 전체 스키마는 별도 최신 명세 확인이 필요합니다. 상세 image_url/description 등의 기존 검증을 목록 응답만 보고 임의로 완화하지 않았습니다.

개발 테스트 모드와 홈 예시 시장 미리보기도 같은 목록 요청 형식을 사용합니다. 테스트 category_id는 예시 값이며 실제 DB 매핑으로 간주하지 않습니다. 미리보기 상품의 예약은 실제 서버에 전송하지 않습니다. 관심 버튼은 기존 메모리 방식이며 서버 찜 API는 이번 범위에 포함하지 않습니다.

## 카테고리 숫자 ID 확정

사용자 지시로 공통 목록 순서대로 1~9 매핑을 적용했습니다. 1=VEGETABLE(채소), 2=FRUIT(과일), 3=MEAT_EGGS(정육·계란), 4=SEAFOOD(수산물), 5=SIDE_DISH(반찬), 6=PROCESSED_FOOD(가공식품), 7=GRAINS_NUTS(곡물·견과), 8=RICE_CAKE_BAKERY(떡·베이커리), 9=OTHER(기타)입니다. 앞선 ID 미확정/응답에서 확인된 분류만 노출 설명을 대체합니다. productCategories.ts를 공통 기준으로 사용하고 상품별 탭은 전체+9개를 처음부터 고정 노출합니다. 전체는 category_id를 생략하고 나머지는 선택한 숫자 ID로 서버 필터링합니다. 음성 분석/최종 반영에서는 기존 문자열 category 코드를 유지합니다.


## 시장 내 가게 목록의 nullable 필드

사용자 합의에 따라 GET /markets/{market_id}/stores의 stores[].address는 String | null입니다. category와 image_url도 기존 변경대로 String | null을 허용합니다. 필드 누락(undefined)은 허용하지 않습니다. total_count/page/size 및 가게 ID/이름 검증은 유지합니다.

주소가 null 또는 빈 문자열이면 목록에 “주소 정보 없음”을 표시하고, 가게 상세 이동 시 address 라우트 파라미터를 생략합니다. 이미지가 null이면 빈 이미지 영역을 표시합니다. 가게 상세 API 자체의 별도 응답 계약은 목록의 nullable 변경으로 추정하지 않습니다.

검증: node tests/market-stores-api.test.cjs, npm run typecheck.


## 상품 목록 할인 여부 nullable

사용자 합의에 따라 GET /products의 products[].is_on_sale은 Boolean | null입니다. 필드 누락은 허용하지 않습니다. true일 때만 기존 유효 할인 가격 검사를 거쳐 할인을 표시하며 null은 할인 여부 미확정으로 취급해 기본 가격을 표시합니다. 응답의 null을 true/false로 덮어쓰거나 가격 차이로 할인 상태를 추정하지 않습니다. 조회 필터 is_on_sale은 기존 Boolean만 허용하며 명시적인 필터와 맞지 않는 응답을 정상 결과로 받지 않습니다. 다른 상품 필드 및 별도 상세/가게 상품 API의 계약은 이번 변경 대상이 아닙니다.


## 상품 목록 할인 가격 필드명

최신 사용자 지시에 따라 GET /products의 할인 가격 필드는 sale_price(Integer | null)를 사용합니다. 앞선 discount_price로의 변경을 되돌렸으며 타입·검증·화면 표시·테스트 응답도 sale_price로 통일합니다. is_on_sale=true이고 유효한 sale_price가 기본 가격보다 낮을 때만 할인 표시합니다. 0원은 유효하며 null은 할인 가격 없음입니다. sale_price 누락과 discount_price만 있는 응답은 허용하지 않습니다. is_on_sale의 null 허용은 유지합니다.


## 가게 상세 nullable 필드

사용자 합의에 따라 GET /stores/{store_id}의 category, phone, image_url은 String | null을 허용합니다. 세 필드는 생략하지 않으며 null을 빈 문자열로 덮어쓰지 않습니다. store_name, market_name, address, description의 문자열 검증과 가게 ID 일치 검증은 유지합니다. 현재 가게 상세 화면은 세 필드를 직접 표시하거나 문자열 메서드로 처리하지 않아 추가 표시 변경 없이 null 응답을 보관할 수 있습니다. 별도 가게 상품 목록의 500 및 응답 계약은 이번 변경 대상이 아닙니다.


## 가게별 상품 ID·카테고리·이미지 최신 계약

사용자 합의에 따라 GET /stores/{store_id}/products의 listing_id/product_id/store_id/category_id는 양의 Integer입니다. image_url은 String | null이며 필드 누락은 허용하지 않습니다. category는 선택 String으로 누락을 허용합니다. 카테고리 ID로 이름을 임의 추정하거나 category를 만들어 응답에 넣지 않습니다. category의 null 허용은 합의하지 않았습니다.

화면의 상세 이동·관심 목록에는 listing_id를 문자열로 변환하고, image_url=null이면 빈 이미지 영역을 표시합니다. 중복 제거는 응답의 정수 listing_id를 사용합니다. 이 절이 앞선 가게별 상품의 문자열 ID 설명을 대체합니다. 별도 상품 상세 응답 계약은 유지합니다.


## 가게 상세 대표 이미지 영역

사용자 요청에 따라 가게 상세 상단 지도 영역을 가게 대표 이미지 영역으로 변경했습니다. GET /stores/{store_id}의 image_url을 표시하고 null/빈 URL/이미지 로드 실패는 기본 가게 아이콘과 안내를 표시합니다. 지도에서 좌표를 받던 거리 계산과 GPS 권한 요청은 제거했으며 가게 이름·주소·상품 목록은 유지합니다. 이미지 로드 실패는 URL/원본 응답 없이 공통 진단 로거로 기록합니다. 이 절이 앞선 가게 상세 지도·GPS 거리 표시 설명을 대체합니다.
