# 상품 상세 및 예약 API

사용자 제공 상세 명세를 적용했습니다.
상품 상세: GET /products/{listing_id}, 정수 판매 게시물 ID(라우트에서는 숫자 문자열). 기본/세일 가격, 설명, 이미지, 품절 상태를 표시합니다. 400/404/500 오류를 처리합니다.
홈 추천은 GET /recommendations의 실제 문자열 listing_id를 사용하며 일반 상품 상세 및 서버 예약으로 연결합니다. 개발 테스트 로그인에서만 모의 응답을 사용합니다. 실제 가게 상품 목록의 listing_id로 이동합니다. 상세 요청에서 숫자로 변환하지 않고 URL 인코딩합니다. 관심 상태도 listing_id로 구분합니다.

예약: POST /reservations, Bearer JWT, JSON { product_id, quantity, pickup_at, request_note? }.
수량은 양의 정수, 수령 시간은 미래의 30분 단위입니다. POST 중 중복 제출을 막습니다. 400/401/404/409/422/500 오류를 처리하며 성공 응답을 받은 후에만 예약 완료를 표시합니다. 네트워크 오류/잘못된 성공 응답은 예약 처리 여부가 불명확하므로 재시도 전 내역 확인을 안내합니다. 자동 재시도하지 않습니다.
201 응답: reservation_id, user_id, product_id, product_name, store_id, store_name, quantity, unit_price, total_price, pickup_at, request_note, status, created_at, message.

pickup_at 예시에 시간대가 없으므로 현재는 한국 시간(Asia/Seoul)으로 변환한 YYYY-MM-DDTHH:mm:ss 문자열을 전송합니다. 백엔드에서 KST로 해석하는지 반드시 확인해야 합니다. 서버는 영업시간/재고/마감 시각을 최종 검증해야 합니다.
로그인 토큰은 현재 실행 중 메모리 세션에만 있습니다. 만료/앱 재시작 시 다시 로그인해야 합니다. 토큰 재발급 경로는 미제공입니다.
서버 주소가 아직 없어 실제 서버 테스트는 미실시입니다.

가격 이력 API 제안은 price-history-api-proposal.md를 참고하세요. 아직 존재하는 API로 간주하지 않습니다.
수령 시간 UI: 오늘만 선택하며, 현재 시각 이후의 다음 정각/30분부터 당일 23:30까지 표시합니다. 휠은 3줄, 가운데 글자 22입니다. 수량 입력은 제거하고 quantity=1, 요청사항은 생략합니다. 바텀 시트에는 날짜·시간 휠·관심·예약 버튼만 표시합니다.
상품 상세는 최신 백엔드 ProductDetailResponse에 맞춰 정수 ID, nullable category_id/description/image_url 및 market_name을 검증합니다. 상세 응답에 없는 category/is_on_sale/created_at은 요구하지 않습니다.

## 예약 목록·취소 (사용자 제공 상세 명세)

예약 탭은 GET /users/me/reservations?page=1&size=10에 Bearer 토큰을 보내 날짜별 카드로 표시합니다. 전체/예정/완료/취소 필터를 제공합니다. 완료는 status=COMPLETED, 취소는 status=CANCELLED로 서버 필터링합니다. 예정은 여러 상태(PENDING/CONFIRMED/READY)의 OR 필터가 명세에 없어 전체 조회한 페이지에서 해당 상태를 표시하며 더 보기로 다음 페이지를 조회합니다. 날짜는 KST로 표시하며 시간대 없는 pickup_at은 기존 예약 생성 규칙과 동일하게 KST로 해석합니다.

상세 화면은 아래 예약 상세 조회 API를 사용하며 목록 항목은 보조 표시 정보로 사용합니다. 제품 수량은 quantity개, 가격은 total_price를 사용합니다. 단위 문자열 필드는 없어 봉/묶음 등은 추정하지 않습니다. 가게 위치 보기는 해당 store_id의 가게 상세로 이동합니다.

취소 확인 후 PATCH /reservations/{reservation_id}/cancel을 Bearer 인증으로 본문 없이 전송합니다. 성공 응답의 reservation_id/status/cancelled_at/message를 확인한 후에만 로컬 예약 상태를 CANCELLED로 갱신합니다. 완료·취소 항목은 취소 버튼을 숨깁니다. 취소 가능한 예정 세부 상태는 서버가 최종 판단하며 401/403/404/409/500 오류를 안내합니다. 네트워크/응답 오류는 성공으로 처리하거나 자동 재전송하지 않습니다. 상세는 현재 목록 스냅샷이며 409 발생 시 목록 재조회로 상태를 확인할 수 있습니다.

개발 테스트 모드에는 14개 예시 예약과 상태별 조회·페이지 처리·사용자별 취소 결과가 있습니다. 첨부 달력 SVG는 예약 상세의 픽업 시간 행에 적용했습니다. UI는 SafeAreaView 안에서 헤더/스크롤/하단 버튼/공통 내비게이션을 분리하고 본문과 버튼에 동일한 최대 폭 및 좌우 여백을 사용합니다. 실제 기기와 서버 검증은 별도 필요합니다.

## 상품 목록 ID 최신 호환

GET /products의 사용자 제공 최신 응답은 listing_id=Integer입니다. 라우트/관심 상태는 String으로 변환하며 상세 응답의 listing_id는 양의 정수 또는 기존 문자열을 허용하고 String으로 비교합니다. 기존 문자열 판매 게시물 ID를 Number로 바꾸지 않습니다. 상품 상세의 나머지 필드는 아래 최신 백엔드 구조를 따릅니다. 예시 시장에서 조회한 상품은 상세에서도 preview 플래그를 유지해 실제 상품 요청/예약과 혼동하지 않습니다.

## 예약 생성 최신 명세 (이 절이 기존 생성 설명을 대체함)

POST /reservations는 정수 listing_id/product_id, 양의 정수 quantity, 시간대가 있는 pickup_at 및 선택 request_note/request_id를 보냅니다. 화면 라우트의 ID는 양의 정수 또는 정수 문자열인지 확인한 뒤 JSON 숫자로 전송하며 listing_/product_ 접두사를 임의로 해석하지 않습니다. pickup_at은 YYYY-MM-DDTHH:mm:ss+09:00으로 전송합니다. user_id/store_id는 보내지 않습니다.

상품 상세의 추천 출처 requestId가 있을 때만 request_id를 전달하며 일반 예약은 생략합니다. 홈 추천 카드는 원본 request_id를 상품 상세 라우트의 requestId로 전달합니다. 서버가 예약 성공 후 RESERVATION 행동 이벤트를 기록하므로 프론트는 추가 이벤트 요청을 보내지 않습니다.

201 응답의 정수 reservation_id/user_id/listing_id/product_id/store_id와 상품명/가게명/가격/픽업 시간/상태/메시지를 검증합니다. 요청 대상과 수량, 픽업 시간이 일치해야 하며 상태는 최초 생성 명세대로 PENDING입니다. 프론트는 상태 변경 필드를 추가 전송하지 않습니다. 오류/잘못된 응답/네트워크 실패를 성공으로 처리하거나 자동 재전송하지 않고 내역 확인을 안내합니다. 기존 UI의 수량=1 및 오늘 30분 단위 픽업 선택은 유지합니다.

예약 생성·상세·목록·취소는 정수 ID를 사용합니다. 접두사가 붙은 문자열 ID는 예약 생성 명세에서 허용하지 않습니다. 개발 예시 상품은 기존처럼 서버 예약을 전송하지 않습니다.


## 방문 수령 선택 시간
시간 선택 화면을 연 시각 기준으로 오늘 오전 9시부터 오후 7시까지 30분 간격으로 표시합니다. 지난 시간은 제외하고 정각/30분과 정확히 일치하면 해당 시간을 포함합니다. 오후 7시가 지난 경우 오늘 예약 마감 안내를 표시합니다. 서버의 최종 예약 검증은 유지합니다.
상품 상세의 시장명은 상품 상세 응답 market_name을 표시합니다. 시장명을 얻기 위한 추가 가게 조회는 하지 않습니다. 홈 추천 상품은 추천 API 응답을 사용하며 실제 판매 게시물 상세로 연결합니다. 추천 응답에 없는 이미지·시장명 처리 방식은 recommendations-api.md를 참고합니다.


## 예약 상세 조회 및 픽업 QR

사용자 제공 상세 명세에 따라 GET /reservations/{reservation_id}를 고객의 Bearer 토큰과 양의 정수 예약 ID로 호출합니다. 예약 목록은 기존 정수 ID 계약을 유지하며 reservation_501 등의 문자열에서 숫자를 추측하지 않습니다. 상세 응답의 상품명/가게/수량/총금액/상태를 우선 표시하고, 상세 명세에 없는 시장명·수령 시각은 기존 목록 정보를 사용합니다.

예약 상태가 READY인 경우에만 서버의 qr_code_data와 qr_code_expires_at을 표시합니다. PENDING·CONFIRMED·COMPLETED·CANCELLED에는 두 값이 null이어야 합니다. 프론트에서 임의 토큰을 만들지 않습니다. QR 이미지는 서버 토큰 문자열 그대로 로컬에서 생성하며, QR 데이터는 로그·영구 저장소에 남기지 않습니다.

화면 진입/복귀와 앱 전경 복귀 시 상세를 재조회합니다. 서버가 정하는 24시간 유효기간을 그대로 표시하고 만료된 QR은 숨깁니다. QR 다시 발급받기는 같은 상세 GET을 호출하며 유효 토큰 재사용/만료 토큰 갱신/이전 토큰 무효화는 서버 책임입니다. 예약 취소 성공 시 QR을 즉시 숨기고 이전 상세 요청 응답이 다시 표시하지 못하도록 막습니다. 조회 실패·완료·취소 상태에는 QR을 표시하지 않습니다. 상인 마이페이지의 픽업 QR 스캔 메뉴는 POST /reservations/pickup/verify로 연결합니다.

### 테스트 고객 확인 방법
테스트 고객으로 로그인 → 판매 중인 실제 테스트 ID 상품(예: 추천 목록의 사과)을 선택 → 미래의 수령 시간으로 예약 → 상세 화면에서 PENDING 상태와 QR 미발급 안내 확인. QR 예시는 예약 탭의 첫 번째 READY 예약(501)을 선택하여 확인합니다. 테스트 토큰은 TEST_ONLY_PICKUP으로 시작하며 실서버에서 사용할 수 없습니다. 재조회 시 유효 토큰을 재사용하고 24시간 경과 후 교체하며, 취소·완료 상태에는 QR을 제공하지 않습니다. 계정마다 예약 데이터와 QR을 분리합니다.

QR 표시 예시는 assets/pickup-qr-test.png를 참고합니다. 해당 파일 역시 유효한 픽업 인증 정보가 아닌 테스트 문자열만 담고 있습니다. 렌더러는 기존 react-native-svg 위에서 동작하는 react-native-qrcode-svg를 사용합니다: https://github.com/Expensify/react-native-qrcode-svg


## 예약 생성 및 QR 상태 규칙

- POST /reservations는 기존 요청 필드를 유지하며 생성 응답의 상태는 PENDING입니다. 상태를 READY로 강제하거나 별도의 상태 변경 요청을 보내지 않습니다.
- 생성 성공 후 상세 화면은 GET /reservations/{reservation_id}를 사용합니다. QR은 READY일 때만 표시하며 다른 상태의 QR 관련 필드는 null입니다.
- 생성 응답의 정수 reservation_id로 상세 조회 화면에 이동합니다. 라우트 파라미터에서만 문자열로 직렬화하며 접두사 ID에서 숫자를 추측하지 않습니다.
- 테스트 서버도 새 예약을 PENDING으로 생성합니다. 기존 READY 예시 예약에서 테스트 QR을 확인할 수 있습니다. 테스트 QR은 실제 픽업 인증에 사용할 수 없습니다.
- POST /reservations/pickup/verify의 READY 상태 검증은 기존 명세를 유지합니다. 상인용 QR 스캔·검증 화면은 아래 절을 참고하세요.

## 상인 QR 스캔 및 픽업 완료

상인 마이페이지 → 픽업 QR 스캔에서 카메라 권한을 요청하고 QR만 인식합니다. 화면 이탈 또는 앱이 백그라운드로 이동하면 카메라를 해제합니다. QR 원문은 저장·로그·URL에 남기지 않고 기존 Bearer 인증과 JSON { qr_code_data }만 POST /reservations/pickup/verify로 전송합니다. HTTP 200 및 COMPLETED 응답을 검증한 뒤 상품명·가게명·예약 번호·완료 시각을 표시합니다. 진행 중 연속 인식을 잠그고 성공/실패 후 사용자가 다시 스캔 버튼을 누르기 전까지 추가 요청을 보내지 않습니다. 네트워크 실패 시 자동 재시도하지 않으며 완료 여부 확인을 안내합니다.

400/401/403/404/409/410/500은 명세에 맞는 안내로 구분합니다. 가게 소유권·READY 상태·만료·일회성 토큰·해시 저장·트랜잭션은 실제 서버에서 검증해야 합니다. 프론트 구현이 이러한 서버 보장을 대체하지 않습니다.

테스트 서버도 저장된 테스트 QR만 검증하고 소유 가게·상태·만료를 검사한 후 한 번만 COMPLETED로 변경합니다. 첫 READY 예시 예약은 테스트 상인 가게(101)에 연결됩니다. 임의 문자열은 실패하며 테스트 결과가 실제 서버에 영향을 주지 않습니다. 고객 상세 재조회 시 완료 상태 및 null QR을 반환합니다. 토큰은 테스트용 메모리 데이터이며 실제 DB 해시/트랜잭션 구현이 아닙니다.

카메라는 설치된 Expo SDK의 bundledNativeModules 기준 expo-camera ~58.0.14를 사용합니다. Expo Go에서 실기기 카메라를 확인할 수 있으며, 자체 개발/배포 빌드는 카메라 권한 플러그인 반영을 위해 재빌드해야 합니다. 실제 기기 레이아웃·권한·스캔 및 백엔드 통합 검증은 별도 필요합니다.

## 예약 생성 ID 정수 타입 수정본

최신 사용자 명세에 따라 요청 listing_id/product_id 및 응답 reservation_id/user_id/listing_id/product_id/store_id를 모두 양의 정수로 검증합니다. 테스트 서버도 숫자 요청·응답을 사용합니다. request_id는 기존처럼 선택 문자열이며 추천 출처가 있을 때만 전달합니다. 추천 AI의 RESERVATION 행동 이벤트는 서버에서 기록하므로 프론트는 별도 이벤트 API 요청을 추가하지 않습니다. 이벤트의 event_id 및 관련 ID도 이번 서버 명세에서 정수로 변경되었으나 프론트가 전송하거나 응답받는 필드는 아닙니다.

## 최신 백엔드 상품 상세 응답 일치

사용자 요청으로 GitHub main의 98a2d8e 커밋을 가져와 backend/schemas.py의 ProductDetailResponse와 backend/routers/products.py를 확인했습니다. listing_id/product_id/store_id/market_id는 정수이며, category_id는 정수 또는 null, description/image_url은 문자열 또는 null입니다. product_name/store_name/market_name은 문자열, price는 정수, sale_price는 정수 또는 null, is_sold_out은 Boolean입니다. 응답에 없는 category/is_on_sale/created_at 검증은 제거했습니다. 임의 접두사 ID를 정수로 해석하지 않습니다.

상품 상세는 sale_price가 null이 아니면 해당 가격(0원 포함)을 표시하고 null이면 price를 사용합니다. 설명이 null이면 생략하고 이미지가 null이면 기존 기본 이미지 영역을 표시합니다. market_name은 상세 응답을 사용하므로 추가 GET /stores 요청을 제거했습니다. 추천·시장·가게 등 모든 상세 진입 경로가 같은 API를 사용하며 추천 request_id 및 예약·찜 연결은 유지합니다. 테스트 상세 응답도 같은 필드 구조를 사용합니다.

## 상인 예약 상태 변경

사용자 제공 명세의 PATCH /reservations/{reservation_id}/status를 상인 Bearer 인증과 JSON {status}로 호출합니다. 요청 ID는 양의 정수이며 응답 reservation_id/status가 대상과 일치하고 updated_at/message가 유효해야 성공으로 표시합니다. 400/401/403/404/409/500을 구분하고 네트워크 실패나 잘못된 응답을 자동 재전송하지 않습니다. 가게 소유권과 허용 상태 전이는 서버가 최종 검증합니다.

백엔드 전달 사항에 따라 예약 번호를 직접 입력하는 화면과 마이페이지 메뉴는 제거했습니다. 소비자는 예약 탭에서 예약을 선택하고 해당 항목의 reservation_id로 GET /reservations/{reservation_id}를 호출합니다. 선택 시 목록에 있는 QR 데이터를 추정하거나 토큰을 직접 생성하지 않으며, 상세 응답의 status가 READY이고 qr_code_data·유효한 만료 시각이 있을 때만 QR 이미지를 표시합니다. PENDING·CONFIRMED·COMPLETED·CANCELLED에는 QR을 표시하지 않습니다. 상인 상태 변경 API 서비스는 유지하되 소비자 화면에서 호출하지 않습니다. 새 상인 예약 목록 API 연결은 아래 절을 참고하며, 고객 전용 상세 API를 상인용으로 재사용하지 않습니다.

QR 자체는 상태 변경 응답에서 요구하지 않습니다. READY가 되면 고객이 기존 GET /reservations/{reservation_id}로 QR을 조회합니다. 실제 토큰 발급·24시간 만료·만료 재발급·이전 토큰 무효화·해시 저장은 서버 책임입니다. COMPLETED는 기존 QR 검증 흐름으로 처리하며 상태 변경 화면에는 바로 완료시키는 버튼을 제공하지 않습니다.

테스트 서버는 제공된 예시 전이 PENDING→CONFIRMED→READY를 지원하고 READY 전환 시각에 테스트 토큰을 발급합니다. 고객 상세 조회가 늦어져도 이 시각부터 24시간을 유지합니다. 유효 토큰 재사용·만료 재발급·완료/취소 무효화를 모의 처리합니다. 테스트 예약 503은 예약 대기, 505는 예약 확인 상태이며 테스트 상인 가게 101에 속합니다. 테스트 계정 재입장 버튼은 기존 정책대로 예시 계정을 초기화하므로 역할을 바꿔 새 테스트 입장하면 고객 예시 예약도 초기화될 수 있습니다. 상태 변경부터 고객 상세·QR 검증까지는 자동 테스트에서 같은 테스트 서버 세션으로 검증합니다.

## 상인 예약 목록 조회 및 관리

사용자 제공 GET /reservations/merchant를 상인 Bearer 인증으로 호출합니다. page/size는 양의 정수이며 기본 1/10, status는 선택 필터이고 전체에서는 생략합니다. store_id/customer_id/위치 필드는 요청에 추가하지 않습니다. 응답은 실제 서버 응답에 맞춰 reservations/total_count/page/size 구조이며 정수 ID·수량·금액, nullable request_note, 5개 상태와 날짜를 검증합니다. 401/403/422/500은 각 안내로 처리하며 미등록 가게 판단은 서버가 수행합니다.

상인 계정은 하단 예약 탭 또는 마이페이지의 예약 관리 메뉴에서 접근합니다. 소비자는 기존 예약 목록·상세·READY QR 흐름을 유지합니다. 상인 화면은 상품·수량·단가·총액·픽업 시각·예약 시각·요청사항과 예약/고객 ID를 표시합니다. 고객 이름·전화번호는 명세에 없어 임의로 조회하거나 표시하지 않습니다.

전체 및 상태별 필터, 더 보기 페이지네이션, 새로고침, 화면/앱 복귀 재조회를 제공합니다. 계정 전환·필터 변경·화면 이탈 이후 오래된 응답은 표시하지 않습니다. 최초 목록 오류와 다음 페이지 오류를 분리하고 같은 예약 ID는 중복 표시하지 않습니다. 비어 있는 목록 안내는 중앙 정렬입니다.

PENDING 행의 예약 확인은 PATCH /reservations/{reservation_id}/status에 CONFIRMED를, CONFIRMED 행의 픽업 준비 완료는 READY를 전송합니다. 번호 직접 입력 없이 해당 행의 ID를 사용하며 사용자 확인 후 요청하고, 서버 성공 전에는 상태를 변경하지 않습니다. 성공하면 목록을 재조회하여 상태 필터와 건수를 맞춥니다. 실패 시 기존 상태를 유지하고 재확인을 안내합니다. READY 행에서 기존 픽업 QR 스캔 화면으로 이동할 수 있고, 스캔 검증 성공 후 목록으로 돌아오면 COMPLETED를 재조회합니다.

QR 발급·토큰 검증·소유권·허용 상태 변경은 서버 책임입니다. 상인 목록에서 고객 전용 QR 상세를 호출하지 않습니다. 고객이 자신의 예약 상세를 열면 READY 토큰을 표시합니다.

테스트 서버도 가게 소속 예약만 최신순으로 조회하고 상태 필터·페이지·요청사항 보존·상태 변경/QR 검증 결과를 반영합니다. 실제 기기 화면 배치 및 운영 서버 통합은 별도 검증이 필요합니다.

상인 예약 목록의 실제 서버 응답은 최초 전달된 items/total과 달리 reservations/total_count를 사용합니다. 사용자가 제공한 실제 응답에 맞춰 서비스 타입·검증·목록 화면·페이지네이션·테스트 서버를 통일했습니다. 개별 예약 필드와 nullable request_note 규칙은 유지합니다.
